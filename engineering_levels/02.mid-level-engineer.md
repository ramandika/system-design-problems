# 02 — Mid-Level Engineer

**Essence**: owns features end-to-end. Designs within an established system, doesn't
design the system itself.

## Scope

- A complete feature across one service (or small cross-service change with a senior
  reviewing the boundaries).
- Accountable for a feature from requirements → design → ship → ops after ship.
- Runs a project thread: breaks work into tasks others (incl. Associates) can pick up.

## System design competency

- **Writes designs for bounded problems**: a new endpoint, a cache, a queue, a table schema,
  a service-internal refactor — with correct back-of-envelope math (per
  `02-scale-estimates.md` in any study case) and stated trade-offs.
- Can reproduce a known architecture from memory (e.g., design a timeline cache like
  [Twitter](../study_cases/02.twitter/03-architecture.md)) and explain each component's why.
- Understands the classic trade-off families: fanout, caching, idempotency, ordering,
  consistency (see the study cases' deep-dive #1s) — and can apply one correctly in a
  familiar context.
- Does not reliably yet: detect that a problem is the wrong problem (framing), make
  trade-offs that span unknowns (new scale, new domain), own a multi-service design alone.

## Technical execution

- Full-stack competence in the team's stack; can touch frontend, backend, storage layers.
- Owns migrations, deploys, config changes for their features; handles on-call for what
  they've shipped.
- Designs and writes the test plan for a feature (unit + integration + the failure mode).
- Comfortable debugging through 2 services of indirection to a root cause.

## Judgment signals

- States trade-offs unprompted in a design doc ("Option A wins X, loses Y, we pick A because Z").
- Sizes work accurately: knows when a 1-day estimate means 3 days, after one probing question.
- Kills scope: finds the smallest version that solves the real problem — and names what was skipped.
- Knows what they don't know, and asks narrowly instead of guessing at boundaries.

## Not expected

- Owning a system's overall architecture or availability target.
- Making org-level or multi-team trade-offs.
- Being the person others escalate to when the system is broken and nobody knows why.

## Growth to next level

Close the gap from feature → system: own a design that spans services and stays correct
under load and failure, and own the aftermath (on-call, degradation, cost). The observable
step-up: problems arrive as "the system behaves badly", not as tickets.
